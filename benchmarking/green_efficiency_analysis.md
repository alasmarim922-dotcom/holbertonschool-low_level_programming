# Green Tech Efficiency & Benchmarking Analysis

## Measurement Methodology
To evaluate software efficiency and understand execution time characteristics, this experiment relies on controlled benchmarking using standard library instrumentation. Specifically, the C standard library's `<time.h>` header and the `clock()` function were used to capture CPU execution intervals. Execution times were normalized to seconds by dividing the difference between start and end clock ticks by `CLOCKS_PER_SEC`. To ensure reliability and minimize environmental noise, all benchmarking runs were executed sequentially within the same local Linux environment under consistent compilation parameters (`gcc -Wall -Werror -Wextra -pedantic -std=gnu89 -Wno-long-long`). 

## Observed Performance Differences
The performance evaluation contrasted two distinct algorithm implementations performing the same core task over an array of size 50,000. The naive implementation (`count_even_naive`), which utilizes nested iteration resulting in $O(N^2)$ complexity, consistently required significantly more CPU time, with recorded execution durations averaging around $0.35$ seconds across multiple trials. In contrast, the single-pass implementation (`count_even_single_pass`), operating at $O(N)$ linear complexity, executed in roughly $0.000$ to $0.001$ seconds. This demonstrates that algorithmic scalability heavily dictates runtime performance, as the naive approach kept the processor active for hundreds of times longer for the identical logical output.

## Relation Between Runtime and Energy Consumption
While direct power draw in watts was not measured via hardware sensors, CPU execution time serves as a direct proxy for active energy consumption in computing systems. Modern processors draw higher dynamic power when executing intensive arithmetic and memory operations. By keeping the CPU active for longer periods—as observed in the naive algorithm's $0.35$-second runtime compared to the near-instantaneous single-pass execution—unoptimized code directly translates to sustained electrical draw. At scale, repeating inefficient loops millions of times multiplies energy waste, heating hardware unnecessarily and increasing carbon emissions in data centers or draining battery reserves on client devices.

## Limitations of the Experiment
Several technical limitations restrict the absolute scope of these findings. First, `clock()` measures processor time consumed by the program rather than wall-clock elapsed time, which can introduce variance depending on system scheduler activity and background processes. Second, the experiments were run on a single virtualized development environment, meaning hardware microarchitectures, cache sizes, and CPU frequency scaling could influence exact tick counts. Finally, software efficiency was evaluated purely on execution runtime without tracking memory bandwidth, cache misses, or actual hardware power metrics.

## Practical Engineering Takeaway
The fundamental takeaway from this benchmarking lab is that algorithmic design is a core pillar of sustainable software engineering. Optimizing code efficiency is not merely an exercise in speed; it is an environmental and engineering responsibility. Developers must prioritize algorithmic complexity reduction during the design phase to minimize CPU active cycles, reduce energy footprints, and build scalable systems that perform efficiently under heavy workloads.
